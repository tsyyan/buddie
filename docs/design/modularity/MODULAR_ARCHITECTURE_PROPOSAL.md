# Buddie — Modular Architecture Proposal

Основано на [ARCHITECTURE_AUDIT.md](ARCHITECTURE_AUDIT.md) (коммит `0bc048e`). Метки: **[O]** наблюдено,
**[I]** выведено, **[P]** предлагается. Всё, что помечено [P], в коде отсутствует.

---

## 1. Вердикт по гипотезе Core / Modules / Adapters

Гипотеза **подтверждается в главном и требует трёх поправок**.

Подтверждено **[O]**: ядро контрактов уже существует и не зависит от checker'ов и транспортов (`core.py`,
`modules.py`, `profiles.py`, `receipts.py`). Транспорты отделены и защищены тестом слоёв. Модули проверки названы и
выбираются явно.

Поправки:

1. **Ядро доверия (trust kernel) — отдельный слой, а не часть «Core».** `policy.py`, `winacl.py`, `evidence.py`,
   `runner.py` и правила provenance (`findings.github_provenance`, `effects.own_get`, идентичность хранилища в
   `verify._assess`) — не общая логика, а граница безопасности. Требования к ним другие: никакой модуль не
   расширяет их и не вызывает в обход. Их нельзя складывать в один «Core» с удобными утилитами. **[P]**
2. **Environment не является модулем проверки.** **[O]** `environment.py`, `diagnostics.py`, `freshness.py` выдают
   собственные документы (снапшот, `environment-diagnostics-v1`, freshness), а не findings по утверждениям отчёта. Это
   отдельные **наблюдатели (observers)**. У `diagnostics` уже есть своя модель разрешений, лучшая в кодовой базе.
   Втягивать их в `modules.REGISTRY` значит смешать «проверить утверждение» с «описать машину». **[P]**
3. **History/lineage как модуля не существует.** **[O]** Есть журнал хука (`journal.py`, `logbook.py`) и freshness,
   но нет проверки утверждений об истории. Проектировать такой модуль сейчас преждевременно.

Ещё одно уточнение. Модуль `execution` смешивает проверки улик сессии (`run:` против транскрипта) и проверки состояния
рабочего процесса хука (`choice:` против журнала, work claims против `[mandate]`). Идентификаторы модулей стабильны и
публичны, поэтому их **не переименовываем**. Меняется только то, как модуль получает входы (§4, C3).

## 2. Рекомендуемое разделение

```
                ┌──────────────────────────── Adapters ────────────────────────────┐
                │ cli.py   mcp.py   remote.py   hook.py (+ config, resolved, event, │
                │ context, journal, logbook, suggest, promises, summary-card)       │
                └───────────────┬──────────────────────────────────┬───────────────┘
                                │ assessment(text, Inputs, sel)    │ observers
┌───────────── Core (contracts + orchestration) ─────────────┐  ┌──┴──────── Observers ────────┐
│ core.py  modules.py  profiles.py  findings.py  verify.py   │  │ environment  diagnostics     │
│ receipts.py                                                │  │ probes       freshness       │
└──────────────┬──────────────────────────────┬──────────────┘  └──────────────┬───────────────┘
               │ Module.run(text, Inputs)     │                                │
┌──────────── Modules (checkers) ─────────────┐│                                │
│ sources: verbatim/*, stores                 ││                                │
│ github:  anchors (file/commit/fact), pr/ci  ││                                │
│ execution: run, choice, mandate, patterns   ││                                │
└──────────────┬──────────────────────────────┘│                                │
               ▼                               ▼                                ▼
┌──────────────────────── Trust kernel ────────────────────────────────────────────────────┐
│ policy.py  winacl.py  evidence.py (collector, network_clean)  runner.py  provenance rules │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

Правила направления **[P]** (часть уже проверяется тестами **[O]**):

| Слой | Может импортировать | Не может |
|---|---|---|
| Trust kernel | stdlib; `core` (типы) | модули, observers, адаптеры. Сейчас нарушено: `policy → diagnostics` (C4) |
| Core | Trust kernel, `core` | адаптеры [O, тест есть]; конкретные checker'ы — только через `Module.run` [P] |
| Modules | Trust kernel, `core` (типы), общие libs (`runner`, `verbatim.store`) | друг друга [P]; `verify`; адаптеры [O]; журнал хука [P] |
| Observers | Trust kernel, `core` | модули проверки, адаптеры |
| Adapters | всё выше | — |

**[I] Циклы.** Предложенное направление само по себе ациклично. Существующая SCC из 15 модулей разрывается тремя
рёбрами: `policy → diagnostics` (C4), `anchors → summary` (C2/C3), `effects → freshness` (через вынос общей функции
`ci_evidence` в lib или переход к явному импорту). Сложность добавляется умеренная: новый файл не нужен, нужны
перенос двух функций и один dataclass входов.

## 3. Границы ответственности

| Ответственность | Владелец | Чего не делает |
|---|---|---|
| Что значит слово вердикта (Fact, Reason) | Core: `findings.py` (таблицы) | модуль не создаёт `Finding` сам |
| Provenance улики | Core + Trust kernel (по идентичности объектов) | модуль не сообщает собственную provenance |
| Что блокирует | `core.Policy` → уровни гейта (`config`) → полы защищённой политики | модуль не решает BLOCK/FLAG |
| Что было проверено и что нет | Core: `Coverage`, `Assessment.not_run`, receipt-v1 `scope` | модуль не скрывает свою невыполненность |
| Чтение мира (файлы, сеть, процессы) | модуль, через Trust kernel (`runner`, хранилище, GET-функция из Inputs) | модуль не выбирает источник улик сам (репо, API, журнал приходят в Inputs) |
| Форма receipts | Core: `verify` (v0), `receipts` (v1) | модуль не пишет поля receipt |
| Транспорт, тексты для людей | Adapters | — |

## 4. Минимальный Module API (для первого эксперимента)

Это **внутренний** контракт на stdlib-dataclasses, не публичный plugin API. Он расширяет существующий
`modules.Module`, а не заменяет его. Ниже — целевая форма после R8. Пилот ([PILOT_MODULE_PLAN.md](PILOT_MODULE_PLAN.md))
вводит только поля, нужные `sources`, а остальные добавляются вместе с модулями, которым они нужны.

```python
# buddie/modules.py  [P]
@dataclass(frozen=True)
class Inputs:                       # всё, что модуль может прочитать; ничего сверх этого
    store: object                   # verbatim Store / UnionStore — один экземпляр на проверку
    fetch: bool
    access: str | None
    repos: tuple[Path, ...]
    github: Callable | None         # GET-функция или None (offline)
    transcript: str | None
    journal: tuple[Path, ...] | None  # явный вход для choice: (закрывает C3); None = поведение 2.0.1
    mandate: dict | None            # уже разрешённый конфиг [mandate] или None
    rev: str | None
    numbers: str                    # "gap" | "fail" | "off"

@dataclass(frozen=True)
class Output:                       # сырые строки в словах checker'а, как сейчас
    rows: dict[str, tuple[dict, ...]]   # "quotes", "numbers", "anchors", "mandate"
    executed: frozenset[Check]          # что реально выполнялось (для not_run/receipt-v1)
    unavailable: frozenset[Check] = frozenset()  # выбрано, но нечем проверить (нет [mandate])
    extra: dict = field(default_factory=dict)    # skipped short quotes и т.п. — то, что сейчас считает _assess

API_VERSION = 1

@dataclass(frozen=True)
class Module:                       # существующие поля без изменений
    id: str
    checks: tuple[Check, ...]
    inputs: tuple[str, ...]         # имена полей Inputs; тест: каждое имя есть в Inputs
    summary: str
    run: Callable[[str, Inputs, frozenset[Check]], Output] | None = None   # None: старый путь в _assess
```

Решения по пунктам:

| Пункт | Решение | Почему так мало |
|---|---|---|
| Идентификация | `id` (уже есть, стабилен) | — |
| Capabilities | `checks` (уже есть; каждый Check в одном модуле) | — |
| Регистрация и обнаружение | статический `REGISTRY` (уже есть) | нет загрузки кода, нет entry points |
| Входы | `Inputs`, один на проверку; `Module.inputs` — подмножество его полей | закрывает C3: модуль не читает того, чего нет в Inputs |
| Выходы | сырые строки в словах checker'а + `executed` | Core переводит их в `Finding` по своим таблицам: модуль не может объявить SUPPORTED, минуя таблицу |
| Вызов | `run(text, inputs, selected_checks)` | один синхронный вызов, порядок — порядок реестра |
| Ошибки | исключение модуля не перехватывается и прерывает проверку, как сейчас (fail-closed) | см. §6, инвариант 3: перехват с превращением в GAPS **ослабил бы гейт** (GAPS не блокирует) |
| Версии | `API_VERSION` — константа ядра; в монолите сравнивать не с чем, тест лишь фиксирует её | нужно только при варианте B |
| Отчётность | `executed`, `unavailable` → `Assessment.not_run` и receipt-v1 `scope` (существующие поля) | новых полей receipt не нужно |
| Receipt Contract | не меняется; v0 собирается из `rows`, как сейчас | golden-тесты должны дать байт-в-байт тот же JSON |

**Пока не нужно:** динамическая загрузка; entry points; зависимости между модулями и их разрешение; async и
параллельный запуск; отдельный процесс на модуль; перехват ошибок модулей; новые поля в receipts; переименование
модулей; публичная документация `Module.run` как API для сторонних авторов.

## 5. Capability Discovery

### 5.1 Что уже есть **[O]**

- `buddie modules`, `buddie profiles` (CLI): статический список.
- receipt-v1 `scope.excluded[*].reason`: `profile`, `gate_level`, `call_option`, `unavailable`, плюс `detected`
  (`receipts.py:19-34`).
- `diagnostics`: состояния `allowed`/`denied`/`unavailable`/`unsupported` с кодами причин (`diagnostics.py:289-294`),
  `catalog()` и MCP `environment_snapshot(list=true)`.
- `verbatim.access` для browser без `playwright` даёт ошибку «playwright is not installed», а не падение.

### 5.2 Соответствие запрошенных состояний существующему словарю **[P]**

| Состояние | Для модулей проверки | Существующий источник |
|---|---|---|
| Доступна | выбрана и выполнена | `Assessment.executed` |
| Не установлена | в монолите не бывает; для extra (`browser`) — `unavailable: missing_extra` | `verbatim.access` |
| Отключена | `profile` / `gate_level` / `call_option` | receipt-v1 `excluded.reason` |
| Требует разрешения | только у observers: `denied: not_granted` / `policy_ceiling` | `diagnostics.decide` |
| Недоступна из-за окружения | `unavailable` (нет `[mandate]`); на уровне finding — UNCHECKABLE (offline, нет репо) | receipt-v1, findings |
| Несовместима | не бывает в варианте A; при B — несовпадение `API_VERSION` | — |

### 5.3 Минимальный шаг **[P]**

`buddie modules --json` выдаёт для каждого модуля `{id, checks, inputs, state, reason}`, где состояние вычисляется
**без сети и без чтения репо**: настроен ли GitHub-токен — да/нет, без значения; есть ли `buddie.toml [mandate]`;
установлен ли `playwright`; что разрешает защищённая политика. Новый MCP-инструмент на первом этапе не добавляется:
это меняет `tools/list`, а он фиксирован в каталогах и в CI (`.github/workflows/ci.yml`, job `docker`). Агенту
хватает receipt-v1 `scope`, который уже говорит, что не выполнялось и почему.

## 6. Permissions и границы доверия

### 6.1 Декларация ≠ sandbox

**[O]** Модули — Python-код в том же процессе. Строка `inputs=("repos", "github")` ничего не запрещает: модуль
технически может открыть любой файл и сделать любой запрос. Значит, «разрешения» модуля в монолите — это
**документация, проверяемая тестами** (статический анализ импортов и вызовов), а не механизм контроля.

Реальные границы, которые уже существуют **[O]**:

| Граница | Что гарантирует | Где |
|---|---|---|
| Защищённая политика | агент без повышения прав не может её изменить | `policy.py`, `winacl.py` |
| `runner` | у дочерних процессов нет токена, нет shell, есть таймауты | `runner.py` |
| Worker для regex | regex из `buddie.toml` выполняется в `python -I` без учётных данных | `patterns.py` |
| Remote-поверхность | файловые аргументы удалены из схемы | `remote._DROP` |
| Provenance по идентичности | `COLLECTOR_OBSERVED` только для собственных GET и хранилища buddie | `effects.own_get`, `verify.py:220-225` |
| Токен — только своему API | токен плагина не уходит на API из окружения | `effects.github_get` |

### 6.2 Минимальный контроль полномочий **[P]**

1. Оставить модель «модули — часть buddie, сторонний код не загружается» (`modules.py`, docstring).
2. Добавить тест слоёв для модулей: модуль `sources` не импортирует `effects`/`mandate`/`summary`/`logbook`;
   `github` не импортирует `verbatim`; никакой модуль не импортирует `logbook`/`journal` (журнал приходит через
   `Inputs.journal`). Это проверяемая декларация полномочий для собственного кода.
3. Если сторонние модули когда-нибудь понадобятся, только **вне процесса**: отдельный процесс через `runner`, без
   токена, на вход текст и пути, на выход строки. Его улики всегда `CALLER_SUPPLIED`/`UNKNOWN`, никогда
   `COLLECTOR_OBSERVED`. Его вердикты проходят через таблицы ядра: незнакомое слово даёт `UNRECOGNIZED`. Сейчас это
   не проектируется.

### 6.3 Риски обхода

| Риск | Сейчас | После [P] |
|---|---|---|
| Модуль читает журнал машины в обход входов | есть (C3) | закрыто `Inputs.journal` + тест импортов |
| Модуль сам объявляет provenance | невозможно: provenance ставит Core | без изменений |
| Модуль выдаёт вердикт-слово вне таблицы | даёт `UNRECOGNIZED` → GAPS/UNKNOWN | без изменений |
| Отключение модуля как способ обойти пол политики | закрыто: полы применяются к классам гейта (`resolved.py`) | без изменений |
| Python-код в процессе обходит всё | всегда возможно для кода в процессе | не решается архитектурой; решается тем, что такого кода нет |

## 7. Сохранение проверяемости: инварианты

| # | Инвариант | Гарантирует Core? | Механизм сейчас | Что нужно ещё |
|---|---|---|---|---|
| 1 | Модуль не выдаёт своё утверждение за подтверждённый факт без доказательств | **Да**, пока модуль возвращает слова, а Fact/Provenance ставит Core | `findings.py` (таблицы), provenance по идентичности | API не должен принимать готовые `Finding` от модуля [P, §4] |
| 2 | Отсутствие доказательств ≠ успех | **Да** | невыбранный модуль → `Skip(capability=True)` → GAPS; пусто → EMPTY/NOT_RUN; `UNDETERMINED` → FLAG | тест: модуль с `executed=∅` даёт NOT_RUN/PARTIAL, а не PASS |
| 3 | Ошибка одного модуля не подменяет результаты других | **Частично**: ложного PASS нет, но теряется весь результат | исключение → fail-closed (`hook.failed`; `tests/test_failsafe.py`) | изоляцию пока не делать; добавить тест «ошибка в одном модуле при смешанном тексте → весь ответ возвращён» на уровне модуля. Если изолировать — только так, чтобы ошибка давала outcome ≠ PASS и гейт считал её отказом, а не GAPS |
| 4 | Receipts совместимы с потребителями | **Да**, если v0 собирается так же | golden: `gate_golden.json`, `test_receipts`, `test_buddie` | байтовое сравнение v0/v1 до и после на корпусе (pilot) |
| 5 | Источники, версии, ограничения, происхождение прослеживаемы | **Частично** | `tool.buddie`/`tool.verbatim`, `sha256` снапшотов, `EvidenceRef` | для `choice:` вход (журнал) нужно указывать явно (C3) |
| 6 | Установка расширения не даёт полномочий | **Да, тривиально**: расширений нет | статический реестр, нет entry points | при варианте B — только allowlist по имени и версии; лучше не делать |

Вывод **[I]**. Инварианты 1, 2 и 6 Core гарантирует архитектурно. Инвариант 5 требует закрыть C3, 4 — golden-тестов,
3 — сознательного решения оставить fail-closed. Ни один инвариант не требует sandbox, пока весь код — код buddie.

## 9. Упаковка: вариант A против варианта B

| Критерий | A: модульный монолит (один пакет) | B: независимые пакеты |
|---|---|---|
| Сложность | низкая; уже почти так | высокая: N `pyproject`, namespace-пакеты или entry points |
| Совместимость | одна версия, одна матрица | матрица core × module; нужна проверка `API_VERSION` |
| Тестирование | один `pytest`, golden-тесты целиком | интеграционные тесты комбинаций; golden для каждого набора |
| Обновления | один релиз (`release.yml`, mcpb, Docker, плагины) | несколько релизов; каталоги (MCP Registry, mcpb, плагины Claude и Codex) ссылаются на один пакет |
| Сопровождение | как сейчас | новый release-процесс для каждого пакета; `release_manifest.py` под каждый артефакт |
| Зависимости | ноль runtime; extras для опционального | выигрыша нет: изолировать нечего, кроме `playwright`, а он уже extra |
| Безопасность | нет загрузки кода | entry points = загрузка кода по факту установки; противоречит инварианту 6 без allowlist |
| Размер установки | ~13,7 тыс. строк Python, без зависимостей | экономия незначительна |

**Рекомендация: вариант A.** Вариант B стоит пересмотреть, только если появится модуль с тяжёлой runtime-зависимостью
(не extra) или сторонний автор модулей.

## 10. Что сознательно не делать на первом этапе

- Plugin marketplace, загрузку кода из путей и entry points, dependency resolver.
- Разделение на PyPI-пакеты.
- Перехват исключений модулей с понижением до GAPS.
- Новый MCP-инструмент capability discovery.
- Переименование модулей (`github` содержит и локальные репо-якоря, но id публичен).
- Перенос observers (`environment`, `diagnostics`, `freshness`) в `modules.REGISTRY`.
- Модуль history/lineage.
- Изменение семантики вердиктов, outcome, слов receipt-v0, порядка `blocking`.
- Перевод хука с receipt-v0 на findings целиком: это отдельная работа с golden-тестами, не первый шаг.
- Лицензирование, платные модули, биллинг.
