# BDX-001 Lite — заземление рекомендаций агента на окружение в buddie 2.x

Статус: **смоук-тест выполнен (9 из 9 прогонов, `claude-sonnet-5-5`), но все прогоны несут подтверждённый
конфаунд.** Одобренный способ запуска (`claude -p` без API-ключа) подмешивает в каждое условие сведения о хост-машине
(Windows 11, PowerShell, дату). Хост совпадает с записанным окружением `win-laptop`. Пользователь одобрил прогон с
этим конфаундом; он описан в §4, §10 и `results/smoke/ENV_LEAK.md`. Выводов о гипотезах H1–H3 эти данные не
поддерживают. Наблюдения отделены от интерпретаций и предложений.

## 1. Цель и методика

Вопрос: улучшают ли структурированные наблюдения buddie (`environment_snapshot`) техническую применимость
рекомендаций агента по сравнению с (A) отсутствием диагностики и (B) ограниченной диагностической оболочкой.

- Три условия, одна модель, один текст задачи, одна базовая инструкция; отличается один абзац о доступном
  инструменте. A — без инструментов. B — `run_diagnostics(device, commands[])`: меню из 35 команд, до 8 за вызов.
  C — `environment_snapshot(device, categories[], …)`: собственное описание и схема инструмента buddie
  (`mcp.TOOLS`) плюс аргумент `device`; агент сам выбирает категории.
- B и C: не больше 4 вызовов, одинаковый «конверт» ответа (устройство, время сбора).
- Ответы инструментов воспроизводятся из записей. Эксперимент меряет пользу **контекста**, а не надёжность сети,
  производительность удалённого MCP или безопасность транспорта.
- Каждый прогон — отдельный процесс `claude -p` в пустом временном каталоге, с заменённым системным промптом, без
  встроенных инструментов, без источников настроек (плагины, хуки, CLAUDE.md), без чужих MCP-серверов, без
  сохранения сессии. Событие `init` проверяется: если список инструментов не совпал с ожидаемым, прогон помечается
  как отказ харнесса, и серия останавливается.
- Порядок прогонов перемешан с фиксированным сидом (`results/smoke/plan.json`, сид 20261026).
- Агент заканчивает ответ блоком `result` (исход, команды, факты об окружении с источником, вопрос). Оценщик
  детерминированный: правила-регулярные выражения по командам и тексту, пробы неподтверждённых утверждений по
  предложениям. Проход правил видит только id сценария и ответ — не условие и не вызовы инструментов. Условие
  подключается после: только чтобы решить, было ли уточнение оправдано (это зафиксировано в ground truth заранее для
  каждого условия), и для сводки. Спорные случаи уходят в ручную проверку по слепому пакету (`bdx packet`).
- Ground truth, правила и меню B зафиксированы до любого прогона модели (меню — до написания сценариев).

## 2. Проверенные возможности реализации (Phase 1)

Проверено чтением кода и запуском, если не сказано иное.

**Интерфейсы.** `buddie/diagnostics.py` (реестр категорий, разрешения, сборка документа
`environment-diagnostics-v1`), `buddie/probes.py` (коллекторы), CLI `buddie snapshot --category … --tool …`,
MCP-инструмент `environment_snapshot` (только локально; `remote.py` его не предлагает). Отдельно —
`environment.py` (снапшот `environment-v0`: runtime, репозиторий, артефакты); в эксперименте не используется.

**Категории.** 15 зарегистрированных: `system.os`, `system.shell`, `system.permissions`, `hardware.cpu`,
`hardware.memory`, `hardware.gpu`, `hardware.storage`*, `software.python`, `software.runtimes`,
`software.package_managers`, `software.gpu_stack`, `software.tools`, `development.containers`*,
`development.project`*, `development.repository`* (* — уровень sensitive). Явно не поддерживаются и отвечают
`unsupported`: `network.connectivity`, `network.proxy`, `network.ports`, `system.applications`.

**Разрешения.** Собирается пересечение: запрошено ∩ поддержано на платформе ∩ файл грантов пользователя
(`environment.toml`; `baseline` = все baseline-категории) ∩ потолок защищённой политики. Запрос ничего не выдаёт
(аргумент вроде `consent` делает его недействительным). Категории с путём требуют каталог внутри разрешённого корня.
Для фикстур использовался временный файл грантов (все baseline + `development.containers`, без корней), подставленный
через `APPDATA`/`XDG_CONFIG_HOME` только для процесса сбора; файл грантов пользователя не читался и не менялся.

**Фактический вывод на 5 окружениях** (`fixtures/raw/*/buddie_full.json`, все проходят `diagnostics.problems()`):
все baseline-категории собраны и на Windows, и на Linux (x86_64, aarch64, контейнеры). Наблюдённые ограничения
коллекторов:

| Ограничение | Где видно | Проверено |
|---|---|---|

**Тесты и фикстуры в репозитории.** `tests/test_environment.py` (726 строк), `tests/test_diagnostics.py` (882).
Полный набор тестов репозитория на ветке эксперимента: 1354 passed, 52 skipped (без изменений в `buddie/` и
`tests/`).

**Границы PR #54.** Диагностика — наблюдатель (Observers), не модуль проверки. Харнесс потребляет buddie только как
наблюдателя: записанные документы CLI, `mcp.TOOLS`, `diagnostics.validate/lines/problems` — на чтение. В реестр
модулей проверки ничего не добавлено, архитектурные изменения PR #54 не реализованы. Аргумент `device` и строка
«Runs buddie on the user's device» — принадлежность харнесса (удалённому наблюдателю они понадобились бы), а не
возможность buddie.

## 3. Что сделано

- 12 сценариев в четырёх категориях (`scenarios/scenarios.json`), для каждого — ground truth, релевантные факты,
  ожидаемое поведение, допустимые уточнения, известные провалы, детерминированные правила, покрытие каждого канала
  (`evaluation/ground_truth.json`). Сценарий CTX-3 воспроизводит реальный провал: агент предполагает WSL на Windows и
  предлагает искать Linux-архив локально, хотя связь архива с устройством не установлена.
- Подлинные записи 5 окружений: ноутбук экспериментатора (Windows 11) — локально; четыре Linux-окружения —
  на GitHub-hosted раннерах через временную ветку `bdx-001-lite-collect` (run 40259346935): `ubuntu-24.04`,
  `ubuntu-24.04-arm`, контейнер `python:3.12-slim --memory=2g`, `debian:bookworm-slim` + только `python3`.
  В каждой записи — полный документ buddie (все категории и все инструменты каталога) и вывод всех 35 команд меню B
  в оболочке по умолчанию. Имена пользователя и хоста заменены заглушками; больше ничего не правилось.
- Харнесс (`harness/bdx/`): маршрутизатор ответов, воспроизведение buddie (срез записанного документа с пересчётом
  служебных полей как в `diagnostics.collect`, проверка `problems()`, рендер как в MCP-адаптере), stdio MCP-сервер на
  прогон, бэкенд `claude -p` с проверкой изоляции, план/прогон/оценка/слепой пакет.
- 120 тестов харнесса: согласованность фикстур, изоляция ground truth, загрузка сценариев, маршрутизация,
  сериализация, детерминизм оценки. Все проходят.
- Модельно-независимое измерение объёма контекста (`results/static/context_cost.json`).
## 4. Выполненные тесты и прогоны модели

- `python -m pytest -q harness/tests` — 120 passed. `python -m pytest -q` в корне репозитория — 1354 passed,
  52 skipped.
- **Прогоны модели: 9 из 9** (план `results/smoke/plan.json`, сид 20261026, рандомизированный порядок).
  `claude -p` (Claude Code 2.1.310), модель `claude-sonnet-5-5`, у каждого прогона свежий процесс и пустой каталог.
  Отказов харнесса нет. Проверка `init` во всех 9 прогонах показала ровно ожидаемые инструменты.
- **Конфаунд «контекст хоста» (одобрен пользователем; влияет на все 9 прогонов).** Без API-ключа `claude -p` нельзя
  запустить с `--bare`. Тогда Claude Code сам прикладывает к каждому разговору блок `# Environment` хост-машины
  (`Platform: win32`, `OS Version: Windows 11 Education 10.0.26200`, `Shell: PowerShell`, рабочий каталог, дату) и
  `system-reminder` с e-mail аккаунта. `--system-prompt`, `--tools ""` и `--setting-sources ""` этого не отключают.
  Это показала отдельная проба (`results/smoke/ENV_LEAK.md`). Хост — то же устройство, что запись `win-laptop`.
  Следствия:
  - условие A **не** было «без диагностики»: в двух сценариях смоука (OS-1, CTX-3) оно знало верную ОС и оболочку;
  - в HW-2 (Linux-контейнер) все условия получали неверную ОС.
- Хронология:
  - первый прогон (`CTX-3-A-r1`) выдал «your machine runs Windows 11» без инструментов;
  - проба подтвердила утечку, серия была остановлена, бэкенд получил защиту (без `--bare` не запускается без явного
    `--allow-host-context`);
  - после решения пользователя оставшиеся 8 прогонов выполнены с `--allow-host-context`;
  - `CTX-3-A-r1` шёл с теми же флагами, поэтому возвращён в выборку (поле `readmitted`), а не повторён — это
    сохранило лимит в 9 прогонов.
- Потрачено (по отчёту `claude -p`): прогоны USD 0.237, проба USD 0.0175.
- Ручная проверка всех 9 ответов: `results/smoke/MANUAL_REVIEW.md`. Она **не слепая**: проверяющий знал условия.
  Слепой пакет (`blind_packet.json`) сформирован, но при 9 ответах, где B и C ссылаются на свой инструмент, пользы от
  него мало.

Что было в ответах (из `results/smoke/runs/*.json`):

- **OS-1.** Во всех трёх условиях одна и та же верная строка:
  `python -m venv .venv; .\.venv\Scripts\Activate.ps1; python -m pip install -r requirements.txt`.
  - A записал «Windows 11 with PowerShell» в `environment_facts` с источником **observed**, хотя инструментов у него
    не было.
  - C вообще не вызвал buddie: «I assumed PowerShell on Windows from your environment details».
  - B вызвал `$PSVersionTable.PSVersion` и `py --list`, верно назвал PowerShell 5.1 и Python 3.14.6, упомянул
    `py -3.12`.
- **HW-2.**
  - A выдал рецепт «Windows, PowerShell» с CUDA и fp16 8B: неприменим к Linux-контейнеру без GPU с лимитом 2 GiB.
  - B первым вызовом отправил 8 Windows-команд Linux-устройству (их выбор подсказал контекст хоста). Вторым вызовом
    — Linux-команды: `free -b` отсутствует, `cat /sys/fs/cgroup/memory.max` = 2147483648. Затем B верно описал
    невозможность и альтернативы. Его факты сверены с записью: Xeon Platinum 8573C, 86 GB свободно.
  - C одним вызовом получил `hardware.memory` с `cgroup_limit_bytes` 2147483648 и отсутствие GPU. Но затем модель
    **не поверила наблюдению из-за конфаунда**: «the snapshot reports Linux, while your shell is Windows. So I
    probably looked at a container…». После этого она попросила `nvidia-smi` «на хосте».
- **CTX-3.**
  - A по утёкшему контексту «знал» Windows. Он предложил поиск через `Get-ChildItem` и проверку `wsl --list` до
    любых WSL-шагов.
  - B вызвал `wsl --list --verbose`, увидел «дистрибутивов нет» и прямо это сказал.
  - C (buddie: `list`, затем `system.os`, `system.shell`, `hardware.cpu`, `software.tools`) честно написал «I haven't
    checked whether WSL is installed» — buddie этого не показывает — и задал уточнение. Это допустимый исход, но не
    решение.
  - Ни один прогон не повторил исходный провал (предположить WSL и искать архив Linux-командами).

в OS-1-A.

| остальные 7 | полностью | полностью | на aarch64 `lscpu` называет ядро (Neoverse-N2), а buddie — `not_reported` |

## 7. Где buddie лучше базовой линии или оболочки

- **Наблюдение.** В HW-2 buddie одним вызовом и одной категорией отдал лимит cgroup рядом с памятью хоста. Агенту в
  B понадобились два вызова: первый ушёл на Windows-команды, а очевидная `free -b` в контейнере отсутствует.
- **Наблюдение.** buddie показывает инструменты каталога (например, нет `curl`/`wget` в debian-nopython), чего в меню
  B нет. У каждого факта buddie есть время наблюдения.
- **Интерпретация.** В HW-2 «правильный» факт buddie нашёл быстрее. Решения это не принесло, потому что модель
  сочла наблюдение противоречащим подмешанному контексту хоста. Без конфаунда это преимущество может проявиться —
  это проверяемое предположение, а не результат.

## 8. Где buddie хуже

- **Наблюдение.** CTX-3: отсутствие WSL-дистрибутивов buddie не наблюдает. Агент в C задал уточнение, агент в B
  рекомендовал верные шаги.
- **Наблюдение.** Объём: в 1–38 раз больше текста на тот же факт (§5.2); в смоуке C — самое дорогое условие.
- **Наблюдение.** OS-1-C не вызвал инструмент вовсе. Причина — подмешанный контекст хоста (так модель и сказала),
  а не buddie.
- **Интерпретация.** Ответ buddie не говорит, какое это устройство. Модель в HW-2-C предположила, что buddie
  наблюдал «не тот» компьютер, и buddie нечем это опровергнуть. Удалённому сценарию идентичность устройства
  понадобится.

## 10. Угрозы валидности

- **Контекст хоста (главная угроза, подтверждена).** Все 9 прогонов получили «Windows 11, PowerShell» от
  `claude -p`. Признаки влияния видны в 6 из 9 ответов: OS-1-A, OS-1-C, HW-2-A, HW-2-B, HW-2-C, CTX-3-A. В остальных
  трёх (OS-1-B, CTX-3-B, CTX-3-C) утечка совпадала с наблюдением, и отделить её влияние нельзя.
- **Размер выборки.** n = 3 на условие, 1 повтор. Разница 3/3 против 1/3 возможна и случайно.
- **Метки по самоописанию.** Автоматическая метка берёт исход из блока `result`. В HW-2-B это расходится с
  содержанием. Ручная проверка исправляет, но она не слепая.
- **Пробы допущений.** 4 из 4 срабатываний ложные: условные фразы про WSL, «16 GB» как объём загрузки. Одно
  настоящее допущение пропущено. До полного прогона пробы нужно переписать и проверить на этих 9 ответах.
- **Подлинность и идеализация.** Фикстуры C — срезы реальных документов buddie без добавлений; B — реальные выводы
  команд. Конструирование не идеализировано, но сценарии подбирал экспериментатор, который знает buddie.
- **Неравенство информации** измерено, а не устранено (покрытие, §5.2). В меню B 7 «лишних» команд. В смоуке одна из
  них (`wsl --list`) дала B решающий факт в CTX-3, другая (`Get-Date`) запрошена без пользы.
- **Окружения.** Linux-окружения — CI-раннеры и контейнеры, а не рабочие станции людей. Windows — одна машина.
  Язык системы русский.
- **Сценарная фикция** в CTX-2 (переход на Node 20 после записи) — в смоук не входил.
- **Формат ответа.** Требование блока `result` может само менять поведение; оно одинаково во всех условиях.

## 11. Следствия для Remote Environment Awareness

Наблюдения:

1. Описанная утечка — частный случай общего риска удалённой осведомлённости. Агент получает сведения об окружении
   из нескольких источников: свой рантайм, слова пользователя, инструмент. Без указания, к какому устройству
   относится каждый факт, источники сталкиваются. В HW-2-C верное наблюдение buddie проиграло ложному контексту.
2. Агенту в C не хватило факта о WSL — именно той области, где произошёл исходный провал.
3. Ответ buddie тяжёлый для удалённого канала, когда нужны 1–2 факта.

Предложения (не реализованные возможности): идентичность устройства или подпись наблюдателя в ответе, категория
для WSL-дистрибутивов Windows-хоста, компактный режим ответа. Удалённый канал, relay и компаньон в рамках
эксперимента не реализовывались.

## 12. Рекомендация о расширении до 72 прогонов

**Не расширять на текущем бэкенде.** 72 прогона с тем же конфаундом дадут неинтерпретируемое сравнение A/C и
переоценку A на 7 из 12 сценариев (все Windows). Порядок:

1. Получить чистый запуск: `ANTHROPIC_API_KEY` → харнесс сам включит `--bare`. Перед прогонами сделать пробу
   «перечисли весь полученный контекст» и сохранить её.
2. Исправить оценщик по результатам смоука, до новых прогонов, с фиксацией версии:
   - переписать пробы допущений (условные фразы, единицы измерения);
   - добавить ручное переопределение исхода, когда `clarification` содержит полноценную рекомендацию.
3. Повторить смоук (9 прогонов) на чистом бэкенде.
4. Расширять до 72, только если чистый смоук не покажет новых отказов харнесса.

Отдельно стоит сохранить эти 9 прогонов: это эмпирический результат о том, как подмешанный контекст хоста искажает
работу с наблюдениями.
