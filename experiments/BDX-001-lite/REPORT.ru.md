# BDX-001 Lite — заземление рекомендаций агента на окружение в buddie 2.x

Статус: **харнесс, сценарии, фикстуры и оценщик готовы. Смоук-тест остановлен после 1 из 9 одобренных прогонов:
одобренный способ запуска (`claude -p` без API-ключа) подмешивает в контекст сведения о хост-машине** (ОС, оболочку,
дату, e-mail аккаунта). Условие A перестаёт быть «без диагностики», а для Linux-сценариев все условия получают
неверную ОС. Подробности — §4 и `results/smoke/ENV_LEAK.md`. Сравнения A/B/C нет. Всё, что ниже названо
«наблюдением», получено кодом без модели. Исключение — один прогон, признанный отказом харнесса.

## 1. Цель и методика

Вопрос: улучшают ли структурированные наблюдения buddie (`environment_snapshot`) техническую применимость
рекомендаций агента по сравнению с (A) отсутствием диагностики и (B) ограниченной диагностической оболочкой.

- Три условия, одна модель, один текст задачи, одна базовая инструкция; отличается один абзац о доступном
  инструменте. A — без инструментов. B — `run_diagnostics(device, commands[])`: меню из 35 команд, до 8 за вызов.
  C — `environment_snapshot(device, categories[], …)`: собственное описание и схема инструмента buddie
  (`mcp.TOOLS`) плюс аргумент `device`; агент сам выбирает категории.
- B и C: не больше 4 вызовов, одинаковый «конверт» ответа (устройство, время сбора).
- Ответы инструментов воспроизводятся из записей. Эксперимент меряет пользу **контекста**, а не надёжность сети,
  производительность удалённого MCP или безопасность транспорта.
- Каждый прогон — отдельный процесс `claude -p` в пустом временном каталоге, с заменённым системным промптом, без
  встроенных инструментов, без источников настроек (плагины, хуки, CLAUDE.md), без чужих MCP-серверов, без
  сохранения сессии. Событие `init` проверяется: если список инструментов не совпал с ожидаемым, прогон помечается
  как отказ харнесса, и серия останавливается.
- Порядок прогонов перемешан с фиксированным сидом (`results/smoke/plan.json`, сид 20261026).
- Агент заканчивает ответ блоком `result` (исход, команды, факты об окружении с источником, вопрос). Оценщик
  детерминированный: правила-регулярные выражения по командам и тексту, пробы неподтверждённых утверждений по
  предложениям. Проход правил видит только id сценария и ответ — не условие и не вызовы инструментов. Условие
  подключается после: только чтобы решить, было ли уточнение оправдано (это зафиксировано в ground truth заранее для
  каждого условия), и для сводки. Спорные случаи уходят в ручную проверку по слепому пакету (`bdx packet`).
- Ground truth, правила и меню B зафиксированы до любого прогона модели (меню — до написания сценариев).

## 2. Проверенные возможности реализации (Phase 1)

Проверено чтением кода и запуском, если не сказано иное.

**Интерфейсы.** `buddie/diagnostics.py` (реестр категорий, разрешения, сборка документа
`environment-diagnostics-v1`), `buddie/probes.py` (коллекторы), CLI `buddie snapshot --category … --tool …`,
MCP-инструмент `environment_snapshot` (только локально; `remote.py` его не предлагает). Отдельно —
`environment.py` (снапшот `environment-v0`: runtime, репозиторий, артефакты); в эксперименте не используется.

**Категории.** 15 зарегистрированных: `system.os`, `system.shell`, `system.permissions`, `hardware.cpu`,
`hardware.memory`, `hardware.gpu`, `hardware.storage`*, `software.python`, `software.runtimes`,
`software.package_managers`, `software.gpu_stack`, `software.tools`, `development.containers`*,
`development.project`*, `development.repository`* (* — уровень sensitive). Явно не поддерживаются и отвечают
`unsupported`: `network.connectivity`, `network.proxy`, `network.ports`, `system.applications`.

**Разрешения.** Собирается пересечение: запрошено ∩ поддержано на платформе ∩ файл грантов пользователя
(`environment.toml`; `baseline` = все baseline-категории) ∩ потолок защищённой политики. Запрос ничего не выдаёт
(аргумент вроде `consent` делает его недействительным). Категории с путём требуют каталог внутри разрешённого корня.
Для фикстур использовался временный файл грантов (все baseline + `development.containers`, без корней), подставленный
через `APPDATA`/`XDG_CONFIG_HOME` только для процесса сбора; файл грантов пользователя не читался и не менялся.

**Фактический вывод на 5 окружениях** (`fixtures/raw/*/buddie_full.json`, все проходят `diagnostics.problems()`):
все baseline-категории собраны и на Windows, и на Linux (x86_64, aarch64, контейнеры). Наблюдённые ограничения
коллекторов:

| Ограничение | Где видно | Проверено |
|---|---|---|

| WSL-дистрибутивы хоста не наблюдаются; `runtime_context: native` говорит лишь, что buddie не внутри WSL | win-laptop | запуск + код |

**Тесты и фикстуры в репозитории.** `tests/test_environment.py` (726 строк), `tests/test_diagnostics.py` (882).
Полный набор тестов репозитория на ветке эксперимента: 1354 passed, 52 skipped (без изменений в `buddie/` и
`tests/`).

**Границы PR #54.** Диагностика — наблюдатель (Observers), не модуль проверки. Харнесс потребляет buddie только как
наблюдателя: записанные документы CLI, `mcp.TOOLS`, `diagnostics.validate/lines/problems` — на чтение. В реестр
модулей проверки ничего не добавлено, архитектурные изменения PR #54 не реализованы. Аргумент `device` и строка
«Runs buddie on the user's device» — принадлежность харнесса (удалённому наблюдателю они понадобились бы), а не
возможность buddie.

## 3. Что сделано

- 12 сценариев в четырёх категориях (`scenarios/scenarios.json`), для каждого — ground truth, релевантные факты,
  ожидаемое поведение, допустимые уточнения, известные провалы, детерминированные правила, покрытие каждого канала
  (`evaluation/ground_truth.json`). Сценарий CTX-3 воспроизводит реальный провал: агент предполагает WSL на Windows и
  предлагает искать Linux-архив локально, хотя связь архива с устройством не установлена.
- Подлинные записи 5 окружений: ноутбук экспериментатора (Windows 11) — локально; четыре Linux-окружения —
  на GitHub-hosted раннерах через временную ветку `bdx-001-lite-collect` (run 40259346935): `ubuntu-24.04`,
  `ubuntu-24.04-arm`, контейнер `python:3.12-slim --memory=2g`, `debian:bookworm-slim` + только `python3`.
  В каждой записи — полный документ buddie (все категории и все инструменты каталога) и вывод всех 35 команд меню B
  в оболочке по умолчанию. Имена пользователя и хоста заменены заглушками; больше ничего не правилось.
- Харнесс (`harness/bdx/`): маршрутизатор ответов, воспроизведение buddie (срез записанного документа с пересчётом
  служебных полей как в `diagnostics.collect`, проверка `problems()`, рендер как в MCP-адаптере), stdio MCP-сервер на
  прогон, бэкенд `claude -p` с проверкой изоляции, план/прогон/оценка/слепой пакет.
- 120 тестов харнесса: согласованность фикстур, изоляция ground truth, загрузка сценариев, маршрутизация,
  сериализация, детерминизм оценки. Все проходят.
- Модельно-независимое измерение объёма контекста (`results/static/context_cost.json`).

## 4. Выполненные тесты и прогоны модели

- `python -m pytest -q harness/tests` — 120 passed.
- `python -m pytest -q` в корне репозитория — 1354 passed, 52 skipped.
- **Прогоны модели: 1 из 9, признан отказом харнесса; сравнения нет.** Разрешение на 9 прогонов `claude -p` с
  `claude-sonnet-5-5` было получено. Первый прогон по рандомизированному плану — `CTX-3-A-r1` (условие A, без
  инструментов). Модель ответила: «your machine runs Windows 11».
- **Диагностика.** Сделан один дополнительный вызов с теми же флагами (USD 0.0175 по отчёту CLI). Он показал, что
  Claude Code сам прикладывает к разговору блок `# Environment` (`Platform: win32`, `OS Version: Windows 11 Education
  10.0.26200`, `Shell: PowerShell`, рабочий каталог, дату) и `system-reminder` с e-mail аккаунта. Это происходит
  несмотря на `--system-prompt`, `--tools ""` и `--setting-sources ""`. Проверка изоляции по событию `init` это
  пропустила: она сверяет список инструментов, а не контекст.
- **Почему прогоны остановлены.** Хост-машина и есть записанное окружение `win-laptop`. Для 6 Windows-сценариев
  условие A получало бы ответ, который должны добывать B и C. Для 5 Linux-сценариев все условия подталкивались бы к
  неверной ОС. Для CTX-2 подмешанная дата противоречит дате сценария. Убрать блок можно только через `--bare` /
  `CLAUDE_CODE_SIMPLE=1`, а они принимают лишь `ANTHROPIC_API_KEY` (под OAuth — «Not logged in»). Ключа нет.
- **Сохранено.** Прогон лежит в `results/smoke/runs/CTX-3-A-r1.json` со статусом `harness_failure` и в сводку не
  входит. Бэкенд теперь отказывается работать без `--bare`, если явно не передан `--allow-host-context`, и пишет
  `host_context_injected` в каждый прогон.
- **Потрачено:** USD 0.0173 (прогон) + 0.0175 (проба) по отчёту `claude -p`.

## 5. Количественные результаты

Модельных результатов нет. Есть одно модельно-независимое измерение: сколько байт текста возвращает каждый канал,
чтобы доставить релевантные для сценария факты (запрос именно релевантных команд в B и категорий в C; ответ ровно в
том виде, в каком его получил бы агент).

| Сценарий | окружение | B, байт | C, байт | C/B |
|---|---|---:|---:|---:|
| OS-1 | win-laptop | 657 | 5600 | 8.5 |
| OS-2 | linux-x64 | 1006 | 5295 | 5.3 |
| OS-3 | linux-x64 | 665 | 5295 | 8.0 |
| RT-1 | debian-nopython | 290 | 2413 | 8.3 |
| RT-2 | win-laptop | 144 | 3245 | 22.5 |
| RT-3 | win-laptop | 572 | 4571 | 8.0 |
| HW-1 | win-laptop | 3609 | 3536 | 1.0 |
| HW-2 | linux-container-2g | 110 | 2247 | 20.4 |
| HW-3 | linux-arm64 | 2571 | 4514 | 1.8 |
| CTX-1 | win-laptop / linux-x64 | 1057 / 848 | 3216 / 3350 | 3.0 / 4.0 |
| CTX-2 | win-laptop | 93 | 3584 | 38.5 |
| CTX-3 | win-laptop | 527 | 3216 | 6.1 |

«Всё сразу»: все 35 команд — 6–13 КБ на окружение; все категории и инструменты buddie — 31–33 КБ.

Наблюдение: при точечном запросе buddie возвращает в 1–38 раз больше текста, медиана ≈8. Причина видна в выводе:
MCP-адаптер отдаёт и строки для человека, и JSON с отступами, а у каждого наблюдения есть `basis`, `method`,
`observed_at`, `status`, `reason`, `concerns`. Это байты, не токены и не число взаимодействий; сколько вызовов агент
реально сделает и какие категории выберет, покажут только прогоны.

## 7. Где buddie лучше базовой линии или оболочки

Модельных данных нет. Наблюдаемо без модели: в HW-2 buddie отдаёт лимит cgroup рядом с памятью хоста в одной
категории, а очевидная команда оболочки (`free -b`) там падает; buddie сообщает наличие инструментов каталога
(`curl`, `wget` отсутствуют в debian-nopython), а в меню B таких команд нет; время наблюдения есть у каждого факта.

## 8. Где buddie хуже

Без модели: объём ответа (§5); отсутствие WSL-дистрибутивов, оболочки пользователя на Windows и различия «нет
`python`» / «`python` = `python3`» (§2). Влияет ли это на рекомендации — вопрос для прогонов.

## 9. Ограничения коллекторов и ограничения модели

Разделение будет сделано по прогонам: правило «агент запросил релевантный источник» (`relevant_sources`) отделяет
случаи, где нужного факта не было в канале (коллектор), от случаев, где факт был доступен, но не запрошен или не
использован (модель). Пока известны только ограничения коллекторов (§2).

## 10. Угрозы валидности

- **Подлинность и идеализация.** Фикстуры C — срезы реальных документов buddie без добавлений; B — реальные выводы
  команд. Конструирование не идеализировано, но сценарии подбирались под известные свойства окружений
  экспериментатором, который знает buddie.
- **Неравенство информации между каналами** измерено, а не устранено (таблица покрытия, §5). Меню B содержит 7
  «лишних» команд, которых нет в buddie намеренно (хост, время, PATH, диск, WSL), — выигрыши B за их счёт нужно
  отмечать отдельно.
- **Окружения.** Linux-окружения — CI-раннеры и контейнеры, а не рабочие станции людей (на раннере, например,
  установлены pwsh, docker, conda). Windows — одна машина. Язык системы русский: ошибки PowerShell в B на русском.
- **Сценарная фикция.** CTX-2 опирается на заявление пользователя о переходе на Node 20 после записи: запись
  подлинная, «устаревание» — условие сценария.
- **Правила-регулярки** ломки: перефразирование может дать ложное срабатывание или пропуск. Смягчение — ручная
  проверка по слепому пакету; условия ручной проверки зафиксированы в ground truth.
- **Формат ответа.** Требование блока `result` может само менять поведение; оно одинаково во всех условиях.
- **Модель и CLI.** `claude -p` без `--bare` подмешивает сведения о хосте в каждое условие (§4). Это подтверждено
  и сделало бэкенд непригодным без API-ключа. Проверка по событию `init` ловит лишние инструменты, но не контекст.
  Любой будущий бэкенд нужно проверять пробой «перечисли весь полученный контекст». Число
  повторов (1 в смоуке, 2 в полном) мало для статистических выводов: 9 прогонов — проверка механики и направлений,
  не оценка эффектов.
- **Слепота.** Проход правил слеп к условию; ручной ревьюер видит ответ, а ответ в C может упоминать buddie —
  полная слепота недостижима.

## 11. Следствия для Remote Environment Awareness

Пока без модельных данных. Наблюдаемо: (1) удалённому наблюдателю понадобятся выбор устройства и время наблюдения —
второе у buddie уже есть на каждом факте, первого нет; (2) текущий формат ответа MCP тяжёлый для удалённого канала,
если агенту нужны 1–2 факта; (3) самые «удалённые» по смыслу вопросы — какое это устройство и что на нём было
скачано — buddie намеренно не отвечает. Это предложения для обсуждения, а не реализованные возможности.

## 12. Рекомендация о расширении до 72 прогонов

Не расширять. Сначала нужен чистый способ запуска модели. Варианты:

- **(a) рекомендуется:** `ANTHROPIC_API_KEY` в окружении. Харнесс сам включит `--bare` и выполнит те же 8 оставшихся
  прогона плюс повтор `CTX-3-A-r1`.
- **(b)** запуск `claude -p` с машины, чья ОС не совпадает ни с одним сценарием. Это неполное решение: дата и
  e-mail всё равно попадут в контекст.
- **(c)** прогон с `--allow-host-context` и явной оговоркой. Не рекомендуется: результат для A на Windows-сценариях
  будет неинтерпретируем.

После чистого смоука проверить пробой контекста, долю `NO_RESULT`, использование инструментов в B и C и ложные
срабатывания правил.
